 OTD OUTFIT OF THE DAY Frontend Product Handoff — Balaji What to build • What every interaction must do • What must connect later OTD is a mobile-first AI personal fashion companion. The frontend is not just a collection of screens: it is the user journey that connects the wardrobe, personal style, destination, occasion, weather, mood and AI outfit recommendation. 1. The OTD product you are building The core experience is: the user gives OTD their wardrobe and personal style, tells OTD where they are going and what the occasion/mood is, and OTD returns a personalized outfit using the user's available clothes. Smart Item Upload → AI recognizes clothing and stores item attributes. Digital Closet → user's real wardrobe, organized and searchable. Personal Style Profile → body/fit information, preferences, colors, style identity and goals. Destination Intelligence → destination/venue/context can influence the recommendation. Occasion + Time + Weather + Mood/Vibe → context for the look. AI Outfit Engine → creates a complete look from available wardrobe items. AI explanation → tells the user why the outfit fits the context. AI Stylist chat → user can ask for changes such as different shoes, more casual, more attractive, etc. Save / History → user can save looks and revisit previous recommendations. Virtual Try-On / Avatar → planned capability; frontend should be structured so it can plug in later. Important: do not hard-code AI results or make the UI depend on fake permanent content. Use mock data only while the APIs are being connected. 2. Design language — must stay consistent Primary visual direction: premium, clean, timeless and gender-neutral. Base palette: warm beige/cream + black/charcoal, with restrained accent use. OTD logo and the 'Your style. Every place.' brand language should remain consistent. Typography: elegant serif for major fashion/editorial headings; clean sans-serif for UI/body text. Avoid overly feminine styling, excessive gradients, neon/glowing AI effects or clutter. Cards, buttons, chips and navigation should use one consistent design system. Mobile-first: design for a phone screen first; responsive behavior comes after the mobile structure is correct. Use real clothing imagery where appropriate, but keep image ratios/cropping consistent across the product. All buttons need clear pressed/disabled/loading states. 3. The most important frontend interaction: Create My Look User opens OTD / Home. User selects or enters destination. User selects occasion and time. OTD obtains weather/context when permitted. User selects mood/vibe. Frontend sends the complete context plus the user's relevant wardrobe/profile IDs to the backend. Show a real loading/progress state while the AI pipeline works. Receive recommendation. Render outfit pieces from actual closet items. Allow Why This Look?, Save, Share, Regenerate and Modify. If user modifies the outfit, send the modification plus the current look context back through the API. This flow is the heart of OTD. Every screen should ultimately support making this loop fast, understandable and enjoyable. 6. Data the frontend must be ready to consume User profile: user ID, height/body/fit information, style preferences, colors, goals. Closet item: item ID, image URL, category, subcategory, color, pattern, material when available, style/formality tags, season, status. Context: destination, venue information when available, occasion, date/time, weather, mood/vibe. Recommendation: recommendation ID, selected item IDs, title, explanation, match/relevance information if returned, context snapshot. Saved look: look ID, recommendation ID, selected item IDs, created date, user notes if supported. Try-on request/result: request ID, selected item IDs, avatar/image reference, processing state, result URL. AI chat: conversation ID, current look/recommendation ID, user message, assistant response, updated item selection if returned. 8. What you should NOT hard-code AI outfit names, explanations or match percentages. Weather values. User closet contents. User profile values. Venue intelligence. AI recognition results. Recommendation item IDs. Try-on results. Authentication state. Use clearly labelled mock data during UI development, but keep the data structures close to the eventual API response. 10. Required reusable frontend architecture Reusable Button, IconButton, Chip, Card, Modal/Sheet, Input, Select, Image, Loading, Error, EmptyState and Toast components. Reusable ItemCard for closet pieces and outfit pieces. Reusable ContextChip for occasion, mood, weather and style. Central navigation/state approach so user context is not duplicated across screens. API/service layer separated from UI components. Environment variables for API URLs and service keys; never expose private secrets in the client. Image upload component with progress and failure handling. Consistent skeleton loaders for lists/cards. Accessible touch targets, readable text and clear contrast. Clean Git commits and branch discipline; do not mix unrelated changes in one commit. 11. MVP priority — build in this order P0 — Must work: Login/auth, onboarding/profile, Home, Digital Closet, Smart Item Upload, context input, AI recommendation result, save look, AI modification/chat UI. P1 — Next: History, stronger profile/style editing, richer destination intelligence UI, notifications, improved recommendation details. P2 — Later: Virtual Try-On, Avatar, Explore/social feed, advanced analytics, shopping/affiliate and other expansion features. 12. Definition of Done for every screen Looks correct on the target mobile viewport. Navigation to and from the screen works. Every visible button has a defined action. Every form has validation. Loading, empty, error and success states are handled where applicable. Back behavior is defined. Data is not lost accidentally. API dependency is clearly identified. Mock data can be replaced without rewriting the UI. No private API keys/secrets are stored in frontend code. Components are reusable rather than duplicated. Screen has been tested on at least one iOS and one Android device/emulator if available. Console/runtime errors are resolved before marking complete. 13. Immediate frontend deliverables Create the reusable OTD design system/components first. Create the complete mobile navigation and screen skeleton. Complete P0 screens in the order defined above. Use mock JSON/data objects that mirror the future API structures. Connect screens through the real user journey rather than presenting isolated designs. Coordinate with Vasant before deciding API field names or changing backend contracts. Coordinate with the AI/ML team before assuming what recognition/recommendation data will be returned. Keep a short frontend status: Done / In progress / Blocked / Next. 15. One rule for the OTD frontend Build the interface around the OTD experience — not around individual screens. The goal is not to make a beautiful prototype. The goal is to make every part of OTD ready to become a working product.
